Topic 77's `books-api.js` kept its data in a JavaScript array, which vanishes when the process restarts. This topic is about replacing that array with a real database, and it covers the two most common ways Node projects do that. **Mongoose** is an ODM (Object-Document Mapper) for **MongoDB**, a document database where each record is a JSON-like document. **Prisma** is an ORM (Object-Relational Mapper) for **SQL** databases such as PostgreSQL, MySQL, and SQLite, where data lives in tables with typed columns and relations. They solve the same problem for two different kinds of database.

### Mongoose: a schema in JavaScript for a schemaless database

MongoDB itself will store any shape of document you give it. Mongoose adds the structure back, in JavaScript, before anything reaches the database.

```js
const userSchema = new mongoose.Schema({
  name: { type: String, required: true, minlength: 2 },
  email: { type: String, required: true, validate: { validator: (v) => /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(v) } },
  age: { type: Number, min: 0, max: 130 },
  role: { type: String, enum: ["reader", "author", "admin"], default: "reader" },
});
const User = mongoose.model("User", userSchema);
```

Validation runs entirely inside Mongoose, so `schema-and-validation.js` needs no database. Verified directly:

```text
valid user -> validate() resolved with no errors
valid user -> role defaulted to: reader

invalid user -> validate() rejected with:
  name: Path `name` is required.
  email: not-an-email is not a valid email address
  age: Path `age` (200) is more than maximum allowed value (130).

bad role -> validate() rejected with:
  role: `superadmin` is not a valid enum value for path `role`.
```

One thing worth knowing about old examples you will find online: the synchronous `validateSync()` still works in Mongoose 9, but running it printed `Warning: Mongoose: Document.prototype.validateSync() is deprecated and will be removed in Mongoose 10. Use Document.prototype.validate() instead.` So this topic uses the async `validate()`, which rejects with an error whose `errors` object has one entry per failing field.

### Casting: strings in, real types out, and a failed cast that does not throw

Values from a web form or a query string are strings. When a document is constructed, Mongoose converts each one to the type the schema declares. Verified directly:

```text
price: 29.99 (number)              <- was the string "29.99"
inStock: true (boolean)            <- was the string "true"
releaseDate: 2026-01-15T00:00:00.000Z (instanceof Date: true)    <- was the string "2026-01-15"
```

What happens to a value that cannot be cast is easy to get wrong. A first version of this demo assumed it would throw when the document was constructed, and running it proved that wrong. Verified directly:

```text
broken product constructed without throwing, price = undefined
validate() rejected with: ValidationError
  inner error type: CastError
  message: Cast to Number failed for value "not-a-number-at-all" (type string) at path "price" for model "Product"
```

Constructing the document succeeds, the bad field is silently left `undefined`, and the failure only surfaces as a `CastError` inside a `ValidationError` when `validate()` or `save()` runs. Code that builds a document and assumes any problem would have thrown already is wrong.

### A document has its id before it is saved, and a query is lazy

```text
_id is an ObjectId: true
_id length (hex chars): 24
isNew (not yet saved): true
```

MongoDB's `_id` is generated by Mongoose in your process the moment `new User(...)` runs, not by the database on insert. A query behaves like a description of a request, not the request itself:

```js
const query = User.find({ role: "author" }).where("age").gte(18).sort({ name: 1 }).limit(5).select("name email");
```

```text
query filter : {"role":"author","age":{"$gte":18}}
query options: {"sort":{"name":1},"limit":5}
query fields : {"name":1,"email":1}
query is a thenable (awaiting it runs it): true
```

All of that was built and inspected with no database, which shows nothing is sent until the query is awaited (or `.exec()` is called). `mongoose.isValidObjectId("abc")` returned `false` and returned `true` for a real id, a cheap guard before `findById()`.

### Connecting, and what failure looks like

```js
await mongoose.connect(uri, { serverSelectionTimeoutMS: 2000 });
```

`connection-pattern.js` points this at `127.0.0.1:27017` where nothing is listening. A `curl` to that port exited with code 7 (connection refused), and a second `curl` to a port with a real listener exited 0, so the probe can tell the difference. Verified directly:

```text
readyState before connect: 0 (0 = disconnected)
[event] disconnected

connect() rejected:
  err.name: MongooseServerSelectionError
  err.message: connect ECONNREFUSED 127.0.0.1:27017
readyState after failure: 0
[event] error: MongoServerSelectionError
```

It took about 2.3 seconds, matching the 2000ms limit, and the process exited with code 1. `serverSelectionTimeoutMS` is how long Mongoose keeps looking for a reachable server before giving up. The default is 30 seconds, which makes a wrong connection string look like the app has hung, so setting it lower in development is worth doing.

### Querying before you connect: buffering, then a timeout

A forgotten `await mongoose.connect()` does not produce an immediate "not connected" error. Mongoose holds the operation and waits. `buffering-demo.js` runs a query without ever connecting, with the wait shortened to one second. Verified directly:

```text
readyState: 0 (0 = never connected)
find() rejected after 1005 ms
  err.name: MongooseError
  err.message: Operation `notes.find()` buffering timed out after 1000ms
```

The real default wait is 10 seconds (`bufferTimeoutMS`, shortened here only so the demo finishes quickly), so in a real app this shows up as requests that hang for 10 seconds and then fail.

### Startup order with Express: connect first, or listen first

`express-startup-demo.js` runs the same app two ways with the database down. Verified directly:

```text
connect-first:
  startup failed, not listening: connect ECONNREFUSED 127.0.0.1:27017
  process exit code: 1
  a curl to the app's port afterwards: exit 7, connection refused (it never opened the port)

listen-first:
  listening on 4500 (database not confirmed yet)
  background connect failed: connect ECONNREFUSED 127.0.0.1:27017
  GET /users -> 503 {"error":"database unavailable"} after about 1.01s
  [error-handler] MongooseError: Operation `users.find()` buffering timed out after 1000ms
```

Connecting first means an app that cannot reach its database refuses to start, which a process manager or deployment platform notices immediately. Listening first means the app starts and answers requests, but every route that touches the database stalls for the buffering timeout and then fails. Neither is always right, but the second one hides a broken deployment behind a healthy-looking port. The `/users` handler here is an `async` function with no `try/catch`: the rejected query reached the error-handling middleware by itself, which is the Express 5 behavior from Topic 78.

### Mongoose CRUD (written, not run)

`crud-pattern.js` has the full create, read, update, delete sequence against a live database. It was syntax-checked and executed as far as it can go without a server: it loads, defines the model, and fails cleanly with `crud-pattern failed: connect ECONNREFUSED 127.0.0.1:27017` and exit code 1. The calls after a successful connection were never run.

One detail in it was checked against the installed Mongoose source rather than recalled. In `findByIdAndUpdate()`, the default is to return the document **as it was before the update**. The old fix was `{ new: true }`, and the Mongoose 9.11.2 source marks that as deprecated in favor of `{ returnDocument: "after" }`, which is what the file uses. To run it, start a MongoDB (a local `mongod`, or a free Atlas cluster) and run `MONGODB_URI="mongodb://127.0.0.1:27017/topic80demo" node mongoose/crud-pattern.js`.

### Prisma: a schema file, and a client generated from it

```prisma
model User {
  id    Int     @id @default(autoincrement())
  email String  @unique
  name  String?
  posts Post[]
}

model Post {
  id        Int     @id @default(autoincrement())
  title     String
  published Boolean @default(false)
  author    User    @relation(fields: [authorId], references: [id])
  authorId  Int
}
```

This is not JavaScript. It is Prisma's own language, and it describes real tables, a foreign key (`authorId`), and the relation between them. You run a command to turn it into database tables (a migration), and another to generate a typed client that matches it. Mongoose's schema constrains documents in a database that does not require one; Prisma's schema is the source of truth for the database's structure.

**What was validated.** The Prisma CLI could not start, so `check-schema.js` runs the schema parser that Prisma publishes as WASM (`@prisma/prisma-schema-wasm`, at the exact version tied to the engine commit Prisma 7.10.1 pins), which needs no network and no database. Verified directly:

```text
VALID: prisma/schema.prisma
model User:
  id: Int
  email: String
  name: String?
  posts: Post[]  (relation PostToUser)
model Post:
  id: Int
  title: String
  published: Boolean
  author: User  (relation PostToUser)
  authorId: Int
```

A check that cannot fail proves nothing, so two schemas that should be rejected were run through it:

```text
old-style-datasource-url.prisma ->
  P1012: The datasource property `url` is no longer supported in schema files. Move connection
  URLs for Migrate to `prisma.config.ts` and pass either `adapter` for a direct database connection
  or `accelerateUrl` for Accelerate to the `PrismaClient` constructor.

missing-back-relation.prisma ->
  P1012: The relation field `author` on model `Post` is missing an opposite relation field on the
  model `User`.
```

The first is a change you will hit in older tutorials, which still put the URL in the datasource block. In Prisma 7 the database URL is no longer allowed inside `schema.prisma`. It moves to `prisma.config.ts`, and the running app hands the client a driver `adapter`, which is what `prisma/demo.ts` does. `prisma.config.ts` was checked by importing `defineConfig` from `prisma/config` and calling it with exactly this shape, which it accepted.

**Version choice.** On the day this was built, npm's `latest` tag for `prisma` pointed at `8.0.0-rc.23`, a release candidate, and the previous stable line was `7.10.1`. A learning resource should not teach a release candidate as the default, so everything is pinned to `7.10.1`. The `prisma`, `@prisma/client`, and adapter versions are pinned exactly (no caret) because they are meant to move together.

**The generated client is TypeScript source.** Reading the installed CLI, the `prisma-client` generator accepts `moduleFormat` of `"esm"` or `"cjs"`, and the setting that chooses the generated files' extension accepts only `ts`, `mts`, or `cts`. Since the generated files are TypeScript, `prisma/demo.ts` is TypeScript and runs through `tsx` rather than plain `node`.

**What was not run, and how to run it.** `prisma generate`, `prisma migrate`, and the client were never executed, so `prisma/demo.ts` is unverified. On your machine, from the project root:

```text
npm install
npx prisma migrate dev --name init
npx prisma generate
npx tsx prisma/demo.ts
```

One thing to watch for, because it was not checked: `prisma.config.ts` and `demo.ts` both say `file:./dev.db`, and a relative SQLite path may resolve from a different folder depending on which tool opens it. If you get a "no such table" error, look for where `dev.db` was actually created.

### Mongoose or Prisma

| | Mongoose | Prisma |
| --- | --- | --- |
| Database | MongoDB (document) | PostgreSQL, MySQL, SQLite and others (relational) |
| Where the shape is defined | A JavaScript schema in your code | A `schema.prisma` file |
| Related data | References and `populate()`, or documents nested inside documents | Foreign keys and relations, loaded with `include` |
| Language | Plain JavaScript works fine | Generated client is TypeScript |
| Changing the structure | Change the schema in code; existing documents are not altered | A migration alters the real tables |

For a MERN project, Mongoose is the direct fit. If the data is strongly relational (users, orders, line items, all referring to each other) and you want the database to enforce that, a SQL database with Prisma is the more natural choice. The choice is made by the shape of the data, not by which library is newer.

### Practical tips

- Connect before you listen, and exit non-zero if the connection fails. An app that starts and then fails every request is harder to notice than one that refuses to start.
- Set `serverSelectionTimeoutMS` lower than the default while developing, so a wrong connection string fails in seconds, not half a minute.
- Never build a document and assume a bad value would have thrown. Call `validate()` or `save()` and handle the rejection.
- Pin Prisma's packages to the same exact version, and check the dist-tags before installing: `latest` is not always a stable release.
- Keep database URLs and credentials in environment variables (Topic 79), never in a file you commit.
