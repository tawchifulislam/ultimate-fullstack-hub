# 10. API / System Design Basics

This is the tenth and final section of the Full Stack Skill Roadmap: three topics on what happens to an API once real data and real traffic reach it. A list endpoint has too many rows to send at once (pagination), the same expensive answer is computed again and again (caching), and one client asks for far more than its share (rate limiting). Every topic ships a code folder, and the notes report what was actually observed from running that code, not only what the documentation says. The labs use a real SQLite table of 100,000 rows, a real Chromium for the browser cache, a real Redis server for the shared cache and the shared counters, real scrypt hashing for the login throttling, and real loopback source addresses for the client-identity tests.

## How the section fits together

The three topics are three answers to the same question: how do you stop one request, or one client, from costing the server more than it can afford? Pagination (Topic 1) limits how much a single request can ask for, with a hard cap on the page size. Caching (Topic 2) limits how often the server repeats work it has already done. Rate limiting (Topic 3) limits how many requests one client may send at all. They also stack on the same endpoint. Topic 2's notes reason that a cursor page is a fixed slice of a list and so is safer to cache than an offset page, which changes whenever a row is inserted above it (that reasoning is labelled there as not run).

Pagination is also a topic about untrusted input, which links it back to the Web Security Basics section. The page number, the page size, the sort column and the cursor all come from the client, so they get digit-only checks, a hard cap, an allowlist for the sort column, bound parameters for values, and a cursor that is treated as a position and never as permission. Rate limiting returns to the same idea from the other side: the client's address is input too, and when `X-Forwarded-For` is trusted wrongly an attacker gets a fresh bucket for every request.

Topics 2 and 3 both run into the problems of keeping state in more than one place, and they land on the same lessons. State held in one process is wrong as soon as there are two: in Topic 2 an invalidation in one instance left the other serving the old price (17 against 999), and in Topic 3 an in-memory limiter on three instances allowed 15 of 30 requests against a limit of 5, where one shared Redis counter allowed exactly 5. State held in a process also grows without bound unless something removes it: an unbounded cache held 100,000 entries, and a limiter that never forgets held 10,000 keys until it was swept. In Redis, a key without an expiry is a bug in both topics (a cache key written without `EX` had a `TTL` of -1, and a rate-limit key whose `PEXPIRE` never ran left the client blocked with a `PTTL` of -1). A check followed by a separate write is a race: the fix in both is to make it one atomic step, a `SET NX EX` for the cache lock and a Lua script for the counters, where the read-then-increment version let all 50 simultaneous requests through against a limit of 10.

Several results in this section are easy to get wrong without running the code. A cursor that compares only the sort column with `<` never returned 3533 of the 100,000 rows and raised no error. Binding the sort column as a query parameter, to "be safe", silently sorts nothing. `no-cache` does not mean "do not cache": Chromium stored the response and revalidated it every time, and only `no-store` forbids storing. Node's `fetch` adds `Cache-Control: no-cache` to a request that carries `If-None-Match`, so testing a `304` with it gets a full `200`. A fixed window counter let 20 requests through in 0.2 seconds against a limit of 10. `trust proxy` set too loosely lets an attacker forge a new client address on every request (8 of 8 allowed), and set too tightly behind a proxy it puts every user in one bucket and refuses an innocent one. A per-account login limiter stopped an attacker who used 300 different addresses and also locked out the real user who typed the right password.

## How each topic is structured

Every topic has a `.md` notes file and a code folder of small, runnable examples. The notes report what was actually observed under "Verified directly" callouts, and say so when something was not run. All timings come from one machine and move from run to run, so compare the numbers inside one table with each other and not with the numbers on your machine. Everything was run on Node 22.22.0 with Express 5.3.0. Topics 1 and 2 use Node's built-in `node:sqlite` module, which is why they are run with `--disable-warning=ExperimentalWarning` (the npm scripts already do this).

Topic 1 needs only `npm install` and no browser. In Topic 2, the five demos `cache-aside-demo`, `stampede-demo`, `lru-demo`, `http-cache-check` and `leak-demo` need only `npm install`. `redis-demo` needs the `redis-server` program on your `PATH` (7.0.15 was used) or a `REDIS_URL` pointing at a server of your own, and `browser-cache-lab` needs a Chromium: set `CHROMIUM_PATH` to a Chrome or Chromium you already have (this is how it was run, on Chromium 141), or install one with `npx playwright-core install chromium`, which was not run here. In Topic 3, `distributed-demo` needs `redis-server` in the same way and the other five demos need only `npm install`. The proxy and login demos use extra loopback addresses such as `127.0.0.2` as separate clients, which worked on Linux and was not tested on macOS or Windows, and the login demo takes about half a minute because it really runs scrypt about 520 times.

Some things are labelled as not run, and they are listed in each topic's "does not cover" section. Examples are Topic 1's Prisma, MongoDB, PostgreSQL and MySQL (only SQLite was run) and backward cursors, Topic 2's CDNs and shared proxy caches, `stale-while-revalidate` and write-through caching, and Topic 3's leaky bucket, concurrency limits and load shedding, limits at the CDN or gateway, Redis Cluster, and what a limiter should do when Redis is down. The demo code is teaching code: the `/posts/all` route in Topic 1, the first (leaking) variant in Topic 2's `leak-demo.js` and `NaiveRedisLimiter` in Topic 3 are wrong on purpose, so do not copy them into a real app.

## Suggested capstone exercise

Take the bookshelf API from the Node.js section and make it ready for traffic. Paginate `GET /books` with a cursor on `(created_at, id)` and a strict comparison, cap the page size at 100, validate every page parameter with a Zod schema, take the sort column from an allowlist, and add a `Link` header and a `nextCursor` (Topic 1). Cache `GET /books/:id` with cache-aside and a TTL, delete the entry on every write, protect the hot key with single-flight, bound the cache with `maxEntries`, and send an explicit `Cache-Control` with an ETag, checking the validator before the expensive work. Authenticate before any response cache, put the user into the key of anything personal, and give every Redis key an `EX` if you move the cache to a shared store (Topic 2).

Then limit the traffic. Mount a general limiter first in the middleware chain and a much stricter one on login, key the login by account and also by IP, answer with `429` and a `Retry-After`, and set `trust proxy` to the real number of proxies in front of your app, never `true` where clients can reach it. If you run more than one instance, keep the counters in Redis and make the check and the update one Lua script (Topic 3). Finally, write checks in the style of the section's labs: walk every page of the list while another script inserts and deletes rows and confirm nothing repeats or goes missing, log in as two users and confirm one never receives the other's cached response, send eight requests with a different forged `X-Forwarded-For` each and confirm the limit still holds, and stop Redis in the middle of a run and write down whether your limiter fails open or fails closed and why.
